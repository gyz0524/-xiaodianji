# 开发思路与代码结构

## 从日常动作出发

小店记围绕“建档 → 到货 → 核对库存 → 补货 → 处理临期 → 备份”设计。适合单台固定手机使用，避免为家庭超市增加复杂登录和多人权限操作。

本项目将页面、业务规则和持久化分开。想学习网站开发，可以先改文字和颜色，再增加页面，最后理解数据规则与保存。

## 一次保存经过什么

1. 用户填写表单，界面检查字段并生成核对摘要。
2. 用户确认，生成带唯一 ID 的操作。
3. `applyOperation` 检查规则，产生新的完整数据状态和操作记录。
4. `commitShop` 比较数据库当前版本，在同一事务中写入快照。
5. 事务完成后才显示“已保存到本机”。冲突或失败会提示，不能假装成功。
6. 若选择导出，生成 JSON 文件；用户确认文件保存好后，才记录该版本已经备份。

## 数据关系与计算规则

商品定义规格、计数单位、每箱数量和补货规则。供应商有联系方式，同一商品可以记录多家供应商报价。

库存按批次保存。商品总库存是各批次剩余量的合计，同一商品不同到期日分开管理。进货记录保留当时的商品名称、供应商、数量、金额等，以便追溯。

- 例如一箱 24 瓶、到货两箱，则新增 48 瓶。
- 48 元 / 24 瓶与 45 元 / 24 瓶比较时，折算每瓶 2 元与 1.875 元。
- 库存不多于下限时，建议补货量为目标库存减记录库存，且不生成零数量建议。
- 单纯标记优先销售或打折不会减少库存，也不刷新实际核对时间。
- 到货会同时写入批次、历史和报价。整理清单不等于实际到货，不修改库存。
- 金额按整数分保存；日期按本地日历日处理，跨月保质期注意月底边界。

## 推荐的学习顺序

1. 修改首页文字、作者展示或主题颜色，运行 `npm run dev` 查看。
2. 修改现有页面的小布局，检查手机和电脑宽度。
3. 如增加业务字段，同时检查 `types.ts`、`schema.ts`、表单、操作规则、备份兼容性和演示数据。
4. 修改库存、价格、日期或恢复逻辑时，为实际行为补充测试，再运行 `npm test` 和 `npm run build`。
5. 要验证离线模式，先构建，再运行 `npm run preview`；普通开发模式并不等于生产离线缓存。

## 已有数据与后续升级

不要随意更换正式网站域名、IndexedDB 数据库名称或备份版本。新增必填字段和修改数据结构时，需要设计旧数据迁移，否则已有记录可能无法读取。

更新网站前建议先导出备份。网页可能仍由旧 Service Worker 提供，关闭该网站所有标签页再重新打开后检查版本；不要通过清理网站数据来刷新，因为那会影响本地记录。

如果增加登录、云数据库或多人同步，原有的数据隔离方式会改变，需要另外设计身份验证、授权、同步冲突和备份机制。当前开源版本没有这些功能。
